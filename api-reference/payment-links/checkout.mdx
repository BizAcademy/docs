---
title: "Checkout public"
description: "Affichez un lien et envoyez une demande de paiement au téléphone du payeur."
openapi: "openapi.json POST /payment-links/{code}/checkout"
---

La page hébergée est disponible à l’adresse `https://pay.bizconnectpay.com/link/{code}`. Elle récupère les moyens de paiement disponibles sans exposer le fournisseur utilisé.

Chaque méthode renvoyée par `GET /payment-links/{code}/checkout` inclut `otp_required`. Pour un pays sélectionné, utilisez le même indicateur sur son entrée `operators`. Affichez un champ de code uniquement quand sa valeur est `true`, puis envoyez le code dans `otp_code` au POST de checkout. Certaines méthodes peuvent renvoyer une URL de redirection dans la réponse.

## Paiement par carte

Pour Visa/Mastercard, sélectionnez le pays `XI` (International), la devise `USD` et la méthode `card` si ces valeurs sont retournées par `GET /payment-links/{code}/checkout`. Dans le résultat `countries`, utilisez l'entrée `operators` du pays choisi. N'affichez pas la méthode si elle n'est pas présente : elle dépend de la configuration active des routes et des devises.

Envoyez le `payment_method` tel qu'il apparaît dans le checkout. L'email et le téléphone sont obligatoires pour le POST de checkout ; aucune donnée de carte n'est envoyée à BizConnectPay. Le payeur saisit ses coordonnées bancaires sur la page sécurisée du fournisseur.

Si la réponse contient `data.redirect_url`, ouvrez-la pour permettre au payeur de finaliser la transaction par carte sur la page sécurisée. Gardez la référence de collecte BizConnectPay et confirmez le succès avec l'endpoint de statut ou le webhook avant de livrer la commande.

Exemple de demande de checkout avec carte :

```json Payload
{
  "country": "XI",
  "currency": "USD",
  "email": "client@example.com",
  "phone_number": "+237690000000",
  "payment_method": "card",
  "lang": "fr"
}
```

Exemple de réponse lorsqu'une redirection est nécessaire :

```json 202 Accepted
{
  "success": true,
  "data": {
    "message": "Payment request accepted by the provider.",
    "reference": "BCP8F4C129D7A23COL",
    "payment_reference": "BCP8F4C129D7A23COL",
    "status": "PROCESSING",
    "provider_reference": "external-transaction-reference",
    "redirect_url": "https://checkout.example.com/confirm/card"
  }
}
```

## Méthodes avec lien de paiement

Certaines méthodes, notamment `djamo`, demandent au payeur de terminer l’opération sur une page externe. BizConnectPay renvoie ce lien sous `data.redirect_url`. Affichez un bouton pour ouvrir l'URL; si elle est présente, laissez le payeur suivre les instructions sur cette page. Ne considérez pas la redirection comme une confirmation de paiement.

Exemple de réponse avec une action requise :

```json 202 Accepted — action du payeur requise
{
  "success": true,
  "data": {
    "message": "Payment request accepted by the provider.",
    "reference": "BCP6ABE23E83CF85COL",
    "payment_reference": "BCP6ABE23E83CF85COL",
    "status": "REQUIRES_ACTION",
    "provider_reference": "external-transaction-reference",
    "redirect_url": "https://checkout.example.com/confirm/payment"
  },
  "meta": {
    "correlation_id": "b39b6c1d-d682-4f61-8839-93b8a9bd76e7"
  }
}
```

`reference` est la référence standard de la collecte BizConnectPay (`BCP` + valeur unique + `COL`) et correspond à la référence de transaction affichée dans le tableau de bord. `payment_reference` reste disponible pour les intégrations existantes et contient la même valeur. Le lien de paiement possède sa propre référence : ne l’utilisez pas comme référence de collecte.

Le lien indique uniquement où le payeur poursuit son paiement. Gardez le checkout ouvert et continuez à interroger son endpoint de statut ou attendez le webhook BizConnectPay. Ne livrez pas la commande avant le statut final `COMPLETED`.

<RequestExample>
```bash cURL
curl --request POST \
  --url https://api.bizconnectpay.com/api/v1/payment-links/0PKOW1IM14/checkout \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: checkout-1001' \
  --data '{
    "email": "payer@example.com",
    "phone_number": "+237690000000",
    "payment_method": "MOBILE_MONEY",
    "otp_code": "123456",
    "lang": "fr"
  }'
```

```json Payload
{
  "email": "payer@example.com",
  "phone_number": "+237690000000",
  "payment_method": "MOBILE_MONEY",
  "otp_code": "123456",
  "lang": "fr"
}
```
</RequestExample>

<ResponseExample>
```json 202 Accepted
{
  "success": true,
  "data": {
    "message": "Payment request accepted by the provider.",
    "reference": "BCP6ABE23E83CF85COL",
    "payment_reference": "BCP6ABE23E83CF85COL",
    "status": "CREATED"
  },
  "meta": {
    "correlation_id": "b39b6c1d-d682-4f61-8839-93b8a9bd76e7"
  }
}
```

## Suivre le paiement et rediriger le payeur

La réponse `202` signifie que la demande a été acceptée pour traitement, pas que le paiement est déjà réussi. Conservez `data.payment_reference`, puis interrogez périodiquement le statut public jusqu’à obtenir `COMPLETED` ou `FAILED` :

```bash cURL
curl --request GET \
  --url 'https://api.bizconnectpay.com/api/v1/payment-links/0PKOW1IM14/checkout/status/BCP6ABE23E83CF85COL'
```

La réponse de statut inclut les deux URL configurées sur le lien. Elles peuvent être `null` si le marchand n’en a pas défini :

```json 200 OK — paiement terminé
{
  "success": true,
  "data": {
    "status": "COMPLETED",
    "reference": "BCP6ABE23E83CF85COL",
    "provider_reference": "provider-transaction-id",
    "amount": "100.0000",
    "currency": "XAF",
    "payment_method": "mtn",
    "phone_number": "+237690000000",
    "success_url": "https://merchant.example/checkout/success",
    "failure_url": "https://merchant.example/checkout/failed"
  },
  "meta": {
    "correlation_id": "b39b6c1d-d682-4f61-8839-93b8a9bd76e7"
  }
}
```

Règles côté client :

- `PROCESSING` : continuer à afficher l’attente et à vérifier le statut ; ne rediriger vers aucune URL finale.
- `COMPLETED` : rediriger le navigateur du payeur vers `success_url`, si elle est renseignée.
- `FAILED` : rediriger le navigateur du payeur vers `failure_url`, si elle est renseignée.
- Sans URL correspondante, afficher à la place un écran de résultat local adapté au statut.

Le polling doit s’arrêter dès que le statut est final. Les URL de succès/échec sont des redirections du navigateur, pas des webhooks. Pour recevoir les événements serveur-à-serveur `payment.completed` et `payment.failed`, configurez une souscription webhook pour l’application rattachée au lien et abonnez-vous aux deux événements.
